# Meal routine suggestions and proactive automation

> Implementation specification, 2026-10-13. Work package **MRS-01–05 / NUTR-REC-002**, tracked in [#242](https://github.com/AdamHikl/mizyun/issues/242). The original planning session performed no implementation. Current source/check evidence is recorded separately in [the implementation evidence](MEAL_ROUTINE_SUGGESTIONS_EVIDENCE_2026-10-13.md); Dev/native/pilot/release gates remain open. Thresholds and product benefits below are hypotheses to validate, not established user behavior.

## A. Context and scope

Users can already choose a saved meal and create a recurring schedule, but discovering and configuring it requires initiative. Detect a repeated logging pattern, explain the proposed automation at the moment it is useful, and let the user enable it in one tap.

**Recommendation:** begin with **three consecutive user-local days**, strict meal identity and a consistent consumption time. Offer a compact in-app card after the third confirmed save. Its primary action actually creates the schedule; opening the existing editor is the secondary action. Start automatic logging tomorrow. Detection is automatic; enabling future food records is explicitly authorized by the user.

This extends [recurring meals #183](https://github.com/AdamHikl/mizyun/issues/183) and complements [PC-04 #174](https://github.com/AdamHikl/mizyun/issues/174). It does not require PC-01's full-day nutrition coverage to identify a repeated entry, and does not close #183's existing acceptance gates. Broader nutrition advice and target adaptation still depend on [PC-01 #171](https://github.com/AdamHikl/mizyun/issues/171).

In scope: single-entry meal detection; a clear proposal; durable dismissal; one-tap, retry-safe acceptance; existing-schedule suppression; existing recurring schedule management; ownership, export/erasure and focused evaluation.

Non-goals: fuzzy AI meal identity, grouped multi-entry meal templates, photo recognition, copying retained photos into future entries, new remote push infrastructure, OS widgets, autonomous target/workout edits, or a general-purpose automation platform. No roadmap or product-goal change is authorized by this planning document.

### Delivery and exact interaction

Use one shared compact card on **Home after returning from a meal save**, with the same candidate accessible in **Meals**. A save launched from Meals can reveal it there. Do not force the user to stay in the logging form, replace successful-save navigation, or interrupt a batch of photo drafts. The card occupies a bounded suggestion position near logging actions, below current progress/resume information. Only one prominent automation suggestion is visible at a time.

Illustrative copy, using synthetic food and time:

> **Make this meal automatic?**
>
> You logged “Oats with banana” for 3 days in a row.
>
> Auto-log this serving every day at 08:00, starting tomorrow. You can skip or pause it any time.
>
> **Auto-log daily** · **Change** · **Not now**

Show the latest serving/available nutrition in a compact expandable detail, and the named timezone in schedule details; make it prominent if it differs from the device zone. Do not invent unknown nutrition. The button's accessible description must include meal, cadence, time and start date. “Change” expands the card's bounded schedule editor prefilled with the proposal, including weekdays; saving that adjusted suggestion must use the same atomic acceptance boundary. It must not revert to the editor's current unconditional 08:00 default. Daily starts tomorrow; customized weekdays start on the first selected date on or after tomorrow, displayed before Save. An intentional timezone change regenerates and revalidates the proposal before acceptance.

After success: “Automatic logging enabled from [first selected date]” with **Manage** and **Undo**. Undo stops the newly created schedule through the existing stop boundary; it must never stop a pre-existing schedule returned by conflict recovery. If the result is unknown, show **Retry** and resolve the same operation before offering a new action. Show a distinct “Already scheduled” result with Manage when another device/manual action created an equivalent schedule.

| Delivery option            | Decision               | Reason                                                                                                                                                 |
| -------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Contextual Home/Meals card | MVP                    | Visible where the user logs; shows exact future behavior; works without notification permission.                                                       |
| Modal/pop-up               | Defer                  | Interrupts a completed logging task and competes with the existing reminder and photo-draft flows.                                                     |
| Push notification          | Later, separate opt-in | Useful only if a measured in-app discovery problem remains; adds lock-screen exposure, permissions, delivery and stale-action handling.                |
| Private in-app inbox       | Later                  | Helpful for many suggestion types, but unnecessary for a first single actionable card; Community inbox is not a private health suggestion destination. |
| OS widget                  | Defer                  | Adds platform scope and lacks room for explaining ongoing automatic food creation.                                                                     |

The choice of card is a product inference. Platform guidance establishes that interactive notifications require authorization and recommends requesting it in a meaningful context, not that a specific card placement is proven best. See [Apple authorization guidance](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications?changes=_4) and [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

### Trigger policy v1

1. Evaluate confirmed, persisted entries from a complete bounded **last-seven-local-day** history, ending at the reference instant. A candidate needs matching entries on today, yesterday and the day before. Count each date once. Three entries today do not qualify.
2. Convert `consumedAt` through the accepted IANA timezone; do not use record creation time as consumption time or apply today's UTC offset to historical dates. Recheck timezone on acceptance; hold proposals during a detected device/profile-zone disagreement until the user chooses the zone. Travel never silently changes an accepted schedule.
3. Exclude unconfirmed, deleted and future-consumed entries, plus every entry linked by the server occurrence ledger to an automatic schedule. Also exclude an automatic marker when present. `source: "manual"` and `confirmedByUser: true` do not distinguish generated entries. A generated entry with its client-editable marker removed is still excluded. A deliberate user-created copy is eligible.
4. Use conservative identity: Unicode NFC, trimmed/collapsed explicit JavaScript whitespace and ASCII-only case normalization (non-ASCII case remains exact to avoid locale differences between JS and PostgreSQL) of a specific name; exact canonical basic calories/macros and known grams, with missing versus zero preserved. Ignore advanced nutrients for identity because entitlement changes must not split a routine. Do not match only “Breakfast”, “Lunch”, “Dinner” or another generic label. Keep meaningful numbers/modifiers; do not equate “chicken rice” with “chicken rice with sauce”. This intentionally misses independently estimated photo meals with different numbers; add tolerant/semantic matching only after measuring misses and corrections, with a separate review flow for uncertain matches.
5. Scope v1 to individual food entries. Existing meal groups are not a reusable composite schedule snapshot. Where several matching entries occur on one day, choose the latest qualifying three-day chain with the smallest time spread, using deterministic tie breakers. Do not combine separate breakfast and dinner occurrences into a single cadence.
6. The three consumption times must fit a **90-minute circular local-time window**. Propose the circular median, rounded to 15 minutes. Suppress the one-tap offer if rounding changes the calendar-day interpretation of a near-midnight routine; a future Customize-only variant can handle that case. These are configurable policy-versioned defaults, not behavior-science claims.
7. Offer **daily** as a suggested choice, never assert that three days prove an enduring daily habit. The card states the choice clearly; Change permits selected weekdays. Weekday-only detection, five occurrences in seven days and alternating routines are later extensions requiring their own evidence and copy.
8. Do not generate a fresh offer from historical backfill or an edit event. Fresh display should follow a current-day confirmed save, or the next foreground visit within 24 hours of that save; accepting stale proposals always revalidates live evidence. Edits, deletes and loss of confirmation invalidate supporting evidence.
9. Suppress equivalents using the **current private schedule template**, days/time/zone and enabled/paused/stopped state. Paused schedules still count as existing. Name comparison or `initial_request.source` alone is inadequate. Stop/Undo is a negative signal: do not automatically resurrect that accepted suggestion.
10. Keep at most one prominent candidate; rank exact repeated dates, consistent times and latest relevant save, with stable ties. Start with at most one new offer per account per seven days. Persist first-shown state across devices, expire an ignored card after seven days, and cool down that family for 30 days. **Not now** suppresses the normalized meal-name family for 30 days; **Don't suggest this meal** persists until the user reverses it. A global Suggestions control hides future offers and does not disable schedules already explicitly enabled.

Three days gives an earlier opportunity to save effort than five. It may also catch temporary meal preparation. Test three versus five only after a small pilot establishes that the offer is understood; there is no evidence here that either number is optimal. The server policy is versioned. V1 uses three days; alternate thresholds require a coordinated policy/contracts/copy change so the displayed explanation stays truthful. Accepted schedules and recorded decisions retain their original version.

## C. Staged implementation steps

### MRS-01 — Pure detector and approved behavior

**Files:** [NEW] `packages/core/src/recurring-meal-suggestion.ts` and tests; [NEW] `packages/contracts/src/recurring-meal-suggestion.ts` and tests; [MODIFY] both public indexes, requirements/feature map and applicable capability guidance. Record the accepted identity/decision protocol in an ADR if it establishes the new durable storage/API format.

Inputs: confirmed entries, authoritative generated-entry IDs, private equivalent-schedule projections, decision state, reference instant, named timezone and policy version. Output: a bounded proposal containing candidate ID, source ID/revision, evidence revision digest, days, local time, timezone, proposed start local date, reason code and expiry. Do not expose raw history to analytics. Canonical signatures must agree in TypeScript and SQL; use common fixtures for Unicode, canonical numbers, nulls and dates.

**Exit:** synthetic fixtures exercise three-day success, two-day/no-result, same-day duplicates, name/portion/nutrition differences, null/zero, generated provenance, near-midnight/time-spread rejection, DST, future timestamps and incomplete history. Policy outputs are reproducible, provider-free and cannot write records.

### MRS-02 — Owner-scoped persistence, reads and decisions

**Files:** [NEW] API recurring-suggestion module/repository port and tests; [NEW] Supabase adapter and tests; [NEW] forward suggestion-state migration and real SQL/role fixtures; [MODIFY] API composition and adapter exports. [MODIFY] account contracts/export/clear hooks, export inventory, logging policy and focused tests.

Add `recurring_meal_suggestion_states` with `user_id`, a policy-independent normalized meal-name family key, first-shown/expiry/cooldown, dismissal reason, acceptance operation/result and schedule reference. Store policy version on proposals/evidence/operation receipts, not in the family's uniqueness key: changing three days to five must not reset dismissal, cooldown, acceptance or stopped-schedule suppression. If identity normalization later changes, migrate/alias durable family keys before enabling that change. Retain only the minimal frozen proposal/evidence revision receipt needed for retries; never store photos or duplicate meal history. Enforce owner-leading index, RLS, cross-owner foreign keys, lifecycle barriers and a unique per-owner family record. A shown/decision endpoint records impressions/cooldowns idempotently; proposals can otherwise be computed from fresh reads.

Proposed transport, with final naming settled in implementation: authenticated `GET /recurring-meal-suggestions`; `POST /recurring-meal-suggestions/:candidateId/decision` for shown/not-now/don't-suggest; `POST /recurring-meal-suggestions/:candidateId/accept`; owner-scoped suggestion preference management. Separate feature availability control must leave ordinary meal saves and existing schedules functional.

GET computes a complete bounded history in the current named zone, follows pages, rejects repeated cursors and returns no candidate on completeness-cap exhaustion. Use a private occurrence-ID lookup and current-template schedule projection. Retrieval can run asynchronously after a successful save and on foreground focus; foreground detection has no dependence on mobile background execution or an all-user nightly scan.

Register this durable category in paginated account export and erasure, including cooldown/preferences/acceptance receipts. Account deletion must prevent new accepted schedules and new decision writes; restore reconciliation must honor existing erasure barriers. Redact names, nutrition, source IDs, evidence and fingerprints from logs/analytics. Respect the existing general API error envelope.

**Exit:** real authenticated owner A/B and anonymous select/insert/update/delete/RPC isolation; deleting-account denial; decision state survives API/app restart and another device; pagination and sparse history safe; export/erasure inventory matches all new records.

### MRS-03 — Atomic one-tap acceptance

**Files:** [MODIFY] suggestion module/adapter/contracts; [NEW] acceptance RPC in the forward migration, concurrency/retry fixtures; [MODIFY] API client interfaces/HTTP/disabled implementations and tests.

Persist the mobile operation UUID, immutable evidence proposal, user-authorized final schedule fields and expected owner **before sending**; if persistence fails, send nothing. Keep evidence identity/revisions separate from editable days/time. Server derives identity from the verified principal, recomputes/validates the exact evidence candidate and source revisions, and independently validates the frozen final schedule fields. Customized days/time need not equal inferred defaults. A digest is a consistency check, not authorization. Reject source edits/deletions and unnoticed timezone changes with a refreshable conflict; never silently accept newer nutrition. An explicitly changed timezone must have a freshly revalidated evidence proposal in that zone.

Within one transaction and the existing recurring owner lock: check previously accepted immutable operation first; lock/revalidate source/supporting entries; reread equivalent current schedules and decisions; choose one server schedule UUID for the family; create through existing admission/snapshot behavior; mark **today intentionally skipped in the accepted timezone** through existing `recurring_meal_skip`; commit acceptance and schedule together. Require the skip to succeed or roll everything back. No entry may be created today, including if the proposed time is still in the future. The first eligible occurrence is tomorrow for daily schedules, or the next selected weekday on or after tomorrow for customized schedules.

Apply that skip **only on first creation**. An accepted replay tomorrow returns the prior result before fresh-evidence/skip logic, so it cannot skip tomorrow or create a second schedule. Never skip or delete entries on a pre-existing equivalent schedule: return Already scheduled/Manage. Changed immutable retry inputs conflict. A stopped accepted schedule must remain stopped. Source deletion after successful acceptance does not invalidate a lost-response replay or stop the existing independent schedule snapshot.

Extend manual `recurring_meal_create` in the new forward migration with a reciprocal equivalent-suggestion-linked-schedule check after acquiring the existing owner lock. If suggestion acceptance won first, a subsequent equivalent manual create must reject with an explicit Already scheduled conflict, mapped to the standard409 envelope; mobile offers Manage rather than retrying or changing the pre-existing schedule. If manual create won first, suggestion acceptance returns the existing-schedule outcome. Preserve ordinary manual creation when there is no equivalent suggestion-linked schedule; a lock alone cannot provide this guarantee. Test both orderings. Preserve the existing 20 non-stopped schedule limit, advanced-nutrient entitlement checks at generation and durable deleted-occurrence protection. Do not add `not_before_local_date` or rewrite the worker just to start tomorrow; revisit an explicit boundary if arbitrary future start dates are later required.

**Exit:** two devices/double taps/manual-create races create at most one equivalent schedule; API restart/lost response replays exactly; today never duplicates; tomorrow is not accidentally skipped; failures leave no partial accepted state; source and account deletion races fail safely.

### MRS-04 — Contextual card, customization and controls

**Files:** [NEW] mobile recurring-meals suggestion data/controller/card/retry files and tests with public exports; [MODIFY] Home and Meals hosts, existing editor prefill/acceptance path, account-scoped read-cache invalidation and Suggestions settings; [MODIFY] save-result integration only where needed for a content-free eligibility refresh event. No nutrition/name in route parameters.

Share candidate state between the two hosts, clear/fence it on logout/account switch, and reevaluate after edit/delete/schedule mutation. Keep successful meal saving independent of detection availability. Do not show the card while recovering a meal's unknown result, retaining a photo, showing another consent/reminder modal or handling queued drafts. There must be no second popup layered over the current routine reminder.

Use clear pending/success/already-scheduled/expired/refresh/retry/disabled states. Acceptance and customized Save use the same operation boundary; ordinary manual schedules change only for the explicit equivalent-suggestion conflict above. Reuse the existing management screen for pause, skip, edit and stop. Prefer 44-point accessible targets, scalable text and a scrolling detail instead of a fixed-height modal.

**Exit:** one-tap creates a real persisted schedule, Change uses proposed defaults, account switches drop stale candidates/callbacks, failure never loses a saved meal, dismissal survives relaunch, and all interactions work with small screen/max font/VoiceOver/TalkBack/themes.

### MRS-05 — Pilot, delivery and threshold decision

**Files:** [MODIFY] consent-gated analytics catalog/test fixtures; [NEW] bounded pilot/evidence artifact; [MODIFY] status and linked issue only with qualified evidence.

Begin with synthetic evaluation, then an authorized small adult design-partner pilot. Keep suggested3/suggested5 policy versions deterministic per participant if comparing thresholds; avoid statistical claims from a tiny sample. Measure eligible patterns, actual viewed offers, acceptance/dismissal, seven/fourteen-day continuation, early stop/Undo, duplicate/correction reports, time/taps saved and notification annoyance if notifications are later added. Analytics remains optional; disable/failure cannot block suggestions.

Report user-confirmed manual/copy saves separately from automatically materialized meals. Generated record counts are not retention, meal adherence or confirmed whole-day coverage. Time saved must come from measured logging baselines and user reports, not assumed app-event reductions. Pilot continuation requires no unresolved duplicate/ownership/recovery defect and users understanding that the schedule creates food records even when they do not open the app. Retain three days if useful offers are understood and rarely reversed; tighten toward five or add weekday-specific offers if temporary patterns cause corrections. No numeric conversion target or time-saving claim is asserted before a baseline exists.
