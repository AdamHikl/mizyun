# Community UI rebuild plan

> Work package: COMMUNITY-UI-001 / [#224](https://github.com/AdamHikl/mizyun/issues/224). Prepared 2026-10-07. Status: Quiet feed selected; UI-01 through UI-07 implemented locally. UI-08 automated review/verification is recorded in [implementation evidence](COMMUNITY_UI_REDESIGN_EVIDENCE_2026-10-07.md); Dev deployment and native acceptance remain open. The original research record below is historical. The proposed interface is a new presentation layer over the existing Community rules, with explicitly identified read-capability additions. Design recommendations are hypotheses until usability and native acceptance pass.

## A. Context and scope

### Problem and intended outcome

Community should make five jobs obvious: see what people I follow shared, find and approve people, share something deliberately, encourage or discuss an activity, and talk to an eligible connection. The current implementation exposes these jobs through colorful shortcut cards, settings forms, and an expansion directory. It lacks a dedicated person-profile destination and hides direct messaging behind “Activities & sharing.” The notification inbox uses a chat-like symbol, adding ambiguity between updates and conversations.

Rebuild the information architecture, screen layouts, components, hierarchy, wording, and navigation from scratch. Keep Mizyun's established brand, system typography, emerald accent, shared top header, and five app tabs. Preserve the behavior and privacy boundaries of the existing clients/controllers; avoid carrying forward the shortcut-grid layout simply because it exists.

In scope: every Community entry and return path, enrollment, feed/detail, own and other-person profiles, discovery/invitations, follows/requests/follow back, publishing/update/unpublish, reactions, comments/mentions, direct messages, notifications, groups, challenges, routines/import, separate Community photos, privacy/safety/rules/export/withdrawal, and loading/error/expired/offline states. Include the completed-workout and private-routine entry points outside Community.

This planning phase creates documentation and a synthetic interactive concept only. It does not change application code, schemas, switches, admission, deployment, or release state. Public recommendations/contact matching, automatic publication, new chat attachments/presence/read receipts, photo avatars, public follower graphs, meal/Coach/health sharing, or importing someone else's completed activity are separate product extensions, not implied by this redesign.

### Design direction

Recommended: **quiet feed**. Compact identity rows, readable content, neutral dividers, one emerald action, and recognizable system icons. Activity content occupies the first useful viewport. People and conversation screens use lists; forms appear only while doing a specific task. A grouped-card variant is included for comparison, but the quiet feed is the working recommendation because it leaves more room for content and fewer decorative containers.

### Non-negotiable logic preserved

1. Separate social identity, deliberate adult/rules enrollment, immutable pilot handles, independently chosen discovery/messaging/push/expansion preferences. Joining shares no private history automatically.
2. Following is directional and approval based. Following someone and allowing them to follow me are separate grants; mutual following is the combination, not an automatic side effect of approval.
3. Feed visibility follows still-published artifacts and current eligibility, membership generation, cohort, feature, block, sanction, and relationship authority. A person-profile destination grants no additional access. Another person's follower/following graph remains private.
4. Summary publication includes only its allowlisted projection; duration and detailed exercises/sets remain separate deliberate options. No private title/notes, GPS, biometrics, meals, Coach content, Health records, or private photos are copied into cards. Private edits never silently update published snapshots.
5. Preserve operation UUID replay, version checks, relationship incarnation, quotas/cooldowns, source-delete revocation, and mutation-bound confirmations. A failed/lost response does not become “Done.”
6. Preserve [memory-only Community cache](../apps/mobile/src/features/community/state/read-cache.ts), its original ten-second authority deadline, visibility epochs, and account/generation binding. Expiry/background/account change/denial removes protected presentation. Keep public chrome stable while reauthorizing; do not extend the deadline to make navigation seem faster.
7. Mute, block, report, unfollow, follower removal, and withdrawal remain distinct. Unblock/rejoin restores nothing. Restricted safety/account routes remain reachable while Community is paused or the person is unenrolled.
8. Core rules stay in `packages/core`, process schemas in `packages/contracts`, database code in the Supabase adapter, and composition in the API. Mobile owns presentation and device behavior. Reuse feature public exports; no imports into another feature's internal files.

## C. Detailed design and staged implementation

### Information architecture and return behavior

```text
Mizyun: Home · Workouts · Meals · Coach · Community
Community: Feed · People · Messages · Me
  Feed → Activity → author Profile / Comments / Reactions / Options
       → Share workout → select saved completed session → exact preview
       → Spaces → Groups / Challenges / Shared routines / Community photos
  People → exact handle / Invite link & QR
         → Following / Followers / Requests (received + sent)
         → person Profile → relationship / eligible Message / safety
  Messages → conversations / new eligible contact → Conversation → person Profile
  Me → shared activity / shared routines / approved photos
     → Edit social identity / Invite / Community settings / Safety
  Header bell → Updates → current authorized destination
  Shared header gear → existing application Settings
```

The local four-way selector is a text navigation row immediately below the Community title. It does not create a second bottom tab bar. At maximum text size, it reflows into a two-column destination list with explicit selected state. The five primary app tabs and existing shared branding/settings header stay consistent. The bell has the accessible label “Community updates”; it never opens DMs. There is no repeated subtitle, onboarding banner, shortcut grid, or “start here” card above an already populated feed.

Only Community root destinations show the local selector. Profile, activity, conversation, group, and editor screens have a clear Back control and title. Going back returns to the exact source, selection, and scroll position while its authority remains valid. A notification/deep link with no in-app history uses a defined Community parent. A withdrawn/deleted/expired destination returns a neutral unavailable view plus Back, never a broken or fabricated profile. Modal tasks use Close/Cancel; keyboard dismissal is not task completion.

#### Profile and relationship states

The [existing profile route](../apps/api/src/modules/community/profile-routes.ts) already returns minimal social identity and `relationshipWithViewer`. Bio is returned only to self or an approved follower of that profile. Use it rather than fetching the private account profile. Its combined relationship label is insufficient by itself for every simultaneous incoming/outgoing pending combination. Add bounded caller-owned two-direction target relationship context with request/edge incarnation IDs, or establish complete correct reads of the existing paginated owner lists. An identity absent from the first page does not mean no relationship. Preserve the existing combined label for compatible clients.

| Relationship                 | Primary action                      | Content / messaging                                                                                              |
| ---------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| None                         | Request to follow                   | Minimal authorized identity; “Shared activity is available after approval.” No bio/content teaser/count.         |
| Pending outgoing             | Requested → Cancel request          | No protected content; failed request never receives settled Requested state.                                     |
| Pending incoming             | Approve plus Decline                | Explain that approval lets them see my still-published and future shares. Approval does not make me follow them. |
| Follower only                | Follow back                         | Separate reverse request; no access to their bio/activity merely because they follow me.                         |
| Following only               | Following → relationship menu       | Their still-published authorized artifacts; messaging unavailable until mutual and both opted in.                |
| Mutual                       | Following; Message if eligible      | Both directional grants exist; messaging still requires independent permission.                                  |
| Blocked / missing / inactive | Back; neutral “Profile unavailable” | Do not disclose why. Owner block management is a separate safety route.                                          |

Incoming/outgoing requests may coexist with an approved reverse edge. Show a secondary “They requested to follow you” row where applicable, rather than lose an approval action behind a single badge. Mutations use the displayed request/relationship ID and original operation UUID. Show pending feedback immediately, but change to success only on verified/reconciled outcome. Follow/quota limits appear at the attempted action, not as permanent dashboard counters.

#### Sharing and artifact semantics

Sharing begins from a saved completed workout or Feed → Share workout → completed-workout picker. Selection shows only the owner's local/private source until preview; the final recipient card contains only permitted fields. The audience line says “Current and future approved followers” and explains that already viewed/copied content cannot be recalled. The chosen workout day is labeled separately from when the post was shared; feed ordering uses publication time.

Unshared sessions show Publish after deliberate preview. Already shared sessions show current published snapshot and Edit shared version/Unpublish. These owner actions require a separate owner-only source/version context; the common activity read lacks it. Reuse the existing owner preview and AuthorSharedActivityDto separation, rather than add private source identifiers to recipient projections. Me lists current publications only; unshared/revoked sources remain managed in private Workouts. Removing details requires preview too; changing the published version explains that card reactions reset. A local Save or Finish does not invoke publication. Unpublish says it removes the Community artifact and leaves the private workout saved. If the source changes during preview, retire the confirmation, refresh the preview, and require a fresh decision. Running remains outside social publication unless its separate requirements explicitly add an allowlisted projection.

#### Conversation and safety wording

Message availability is evaluated from mutual approved following, both messaging preferences, feature admission and current authority. Own opt-out leads to messaging settings; no eligible contacts leads to People; other denial uses neutral wording without revealing a peer's private preference or block state. Current contracts support deletion of an own message, not deletion/removal of a chat. The existing Block person action ends both follow directions/requests and removes conversation access; label and confirm it as a block. Do not rebrand it as Delete chat. Messaging-update mute/unmute is global, not a peer-specific conversation setting.

Successful submission can say “Sent” only if it means server acceptance; never say Delivered or Read. Failed send retains the caller-bound draft and offers Retry with the same payload/operation. Draft lifetime must preserve the current privacy policy; do not introduce disk persistence or offline send queues. Message retention and lack of end-to-end encryption are accurately explained in the existing permission/help context. Reporting a message uses existing bounded authority/receipt handling; blocking is separate and immediately retires the visible conversation.

### Shared visual and interaction specification

- Use system type and existing scale as the foundation; proposed semantic sizes are title22–24, section18, body16–17, metadata13–14, all scalable. Essential controls do not depend on tiny captions. Long handle/name/bio text wraps or reveals its full value; translated labels and maximum text do not collide with trailing actions.
- Use existing 4/8/16/24/32 spacing tokens. Standard screen gutter16, row/content separation12–16 where needed, section separation24. Round only genuine cards, media and task surfaces; avoid nested bordered cards and colored feature tiles. Maximum content width remains shared.
- Neutral surfaces and separators carry structure. Emerald communicates one main action and selected state; destructive color accompanies a destructive label. Verify contrast against actual backgrounds; the current emerald token alone is not evidence of compliance. Use an accessible semantic action pairing, preferably Community scoped first, before changing any shared token.
- Identity uses a consistent 40-unit social avatar symbol, 56–64 on profile, not arbitrary emoji decoration. Reactions may use their existing five emoji; navigation uses the established platform/system icon abstraction. Do not introduce a new icon dependency just for Community.
- Every action has a non-overlapping effective target of at least48 units. Labels may visually be compact. Do not make the entire card one nested pressable: author, content and reaction/options actions are separate accessible targets with deliberate order.
- Small options/choice sheets show visible labels and one task. Complex sharing, identity editing, group administration and media tasks get a full-height screen with clear exit. Confirmation names the consequence; a successful harmless action uses inline feedback rather than another modal.
- Main feed/root preserves the app tab bar; task editors/conversation keyboard layout must respect native safe areas and avoid competing bottom chrome. Test Android system Back, iOS swipe Back, modal dismissal, keyboard submit/newline and focus restoration.
- Reduced motion removes cosmetic animation; loading is quiet. Screen reader labels announce purpose, selected/busy/error state and useful activity context. Hide decorative avatars/icons from duplicate announcement; ensure modal focus is contained and restored.
