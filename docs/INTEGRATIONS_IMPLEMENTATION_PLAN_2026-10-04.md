## A. Context and scope

### Product outcome

Make Mizyun easier to use alongside the tools people already have: bring in weight and completed exercise, send deliberately selected Mizyun records to health platforms, migrate lifting history, log workouts from a wrist, and let another developer build a useful experience from a user's explicitly authorized Mizyun data. Measure reduced manual entry and reliable records rather than the number of integrations advertised.

Recommended order: health platforms on both phones → optional account synchronization → selected outbound records → lifting-history migration → watch companions. A small read-only developer pilot can proceed independently after its authorization boundary is proven. Sleep/recovery and individual vendor clouds follow demonstrated demand. These are proposed dependencies, not an accepted change to the repository roadmap.

Deliverables of future implementation: connection settings, purpose-specific permissions, provenance and duplicate handling, record previews/history, correction/deletion reconciliation, export queues, account lifecycle coverage, native watch logging, and a versioned developer API. Each package below is independently reviewable and must remain disabled until its own exit criteria pass.

This planning session does not implement code, migrations, connections, credentials, builds, deployments, Store submissions or data access. Automatic calorie-budget changes, automatic progression, public sharing of imports, medical interpretation, automatic repetition detection, universal vendor support and unrestricted developer writes are outside the initial product scope.

### Connection experience

Account → Health connections should show only available providers and purposes. Keep the existing Steps control and direct route working. For each new type, offer a concrete benefit, then request the smallest OS permission set when the user enables it. Show the actual import range and selected source, rather than promising all history.

Separate controls: **Show on this device**, **Save selected data to my account**, **Export my Mizyun records**, and, later, **Use selected data in Coach**. Developer grants have their own Connected apps page showing recipient, purpose, fields, date range, last access and Revoke. Health connections must not authorize Community sharing.

States include unavailable, permission action needed, readable range limited, ready with no readable records, reading, last successful read, partial results, retry required, disconnected and external cleanup pending. On iOS, absence of records cannot reliably establish read denial or a true zero. Manual Mizyun use remains available when permissions are declined.

Before account synchronization, show categories, date range, expected record count where available, retention and what removing the connection does. A new Mizyun account on the same phone must explicitly confirm the health profile before import: the OS health store is shared device state, not proof of Mizyun account ownership.

### Proposed contracts and storage

Define strict, versioned `HealthObservation` variants rather than turning imported rows into manual body/workout/food records. Proposed envelope: opaque observation ID; provider; record type; external record ID; source app identifier/name where available; non-identifying device category; UTC start/end; original offset/timezone when available; original unit and normalized value; source revision/modification time when supplied; imported time; connection/binding generation; coverage; provenance class; permitted-use lineage. Derive owner from the authenticated principal, never a supplied `userId`. Treat device-supplied provenance as an assertion, not cryptographic vendor verification.

Proposed account tables, introduced only in INT-03: `health_connections` (purpose grants, source/type selection, generation, status); `health_import_records` (typed observations, source key/revision, tombstone, usage lineage); `health_sync_cursors` (per connection/type/device cursor and readable range); `health_export_jobs` / `health_export_mappings` (opaque export identity, version, per-item acceptance/deletion state). No raw provider metadata blob. Add compound uniqueness on owner/connection/provider/type/source-record identity; bounded indexes for dates and lifecycle queries. Final migration names/version timestamps are chosen at implementation, not invented here.

Candidate authenticated owner routes: `POST /v1/health-connections`, `PATCH /v1/health-connections/:id`, `DELETE /v1/health-connections/:id`, `GET /v1/health-observations`, and `POST /v1/health-connections/:id/sync-batches`. Batches have stable operation IDs, bounded size, expected generation, observations/deletions, and a cursor proposal; return a durable receipt. Separate control of disconnect and copy deletion. Schemas must reject arbitrary metadata/unknown fields and unreasonable values without quietly clamping them into plausible readings. Pagination is required; the existing 200-record Body History limit must not truncate merged history silently.

### Synchronization and lifecycle rules

1. Begin with bounded foreground reads and explicit refresh. Request neither background access nor extra history access initially. Health Connect's default historical boundary is 30 days before the **first grant**, not a sliding 30-day window; expose the actual accessible interval. Feature-check later history/background permission. iOS limited-history APIs require installed SDK/OS checks; do not raise supported OS versions merely to use them.
2. Partition local observations, cursors and export queues by environment, account, connection, device and binding generation. Retire async work before logout/account switch. Recheck principal/generation before local persistence, upload and acknowledgments. Existing OS grants must not silently reactivate imports for another Mizyun account.

   Protect local health state/credentials with encrypted or platform-protected storage. Initially exclude observations, cursors, bindings and watch queues from OS cloud backups and device transfers; verify both legacy and modern Android extraction rules rather than relying on `allowBackup` alone. Do not store personal health information in app-managed iCloud. A restore starts unbound/disabled until current account/profile reconfirmation; stale restored state cannot render or upload. Retire and remove persistent watch DataItems/snapshots when account/pairing bindings change. Native spike must verify actual storage and backup behavior.

3. Use HealthKit anchored changes and Health Connect Changes tokens for corrections/deletions when available. Commit a cursor only after observations and tombstones are durably accepted. Replaying an accepted batch is idempotent. Health Connect tokens expire after 30 days unused; recover with a bounded snapshot/dedup pass and disclose unreconciled history outside the readable range.
4. HealthKit deletion notifications and available history cannot guarantee complete reconciliation after prolonged offline periods. INT-03 must establish a tested recovery window; outside it mark records/reconciliation uncertain and block downstream Coach use. Never interpret unreadable/missing iOS data after permission loss as proof that the source deleted records. If account-copy lifecycle cannot meet the published promise, keep that type device-only.
5. Exact source IDs/revisions identify replay. Same time/value across cloud/store sources is a possible duplicate, not proof. Select one authoritative source/channel by type; offer suggestions for overlapping workout records, never automatically delete legitimate sessions. Preserve manual entries separately. Activity/sleep platform aggregates and nutrition have different overlap behavior; no universal “sum everything” rule.
6. Disconnect stops reads/uploads and retires pending work. Removing imported copies deletes local/cloud copies without deleting the original source. Default disconnect flow offers copy removal clearly; keeping an archive requires a separately explained, permitted retention choice and stale status. User deletion installs a suppression tombstone so the next read does not silently recreate the copy. Reconnection/reset of suppressions is deliberate.
7. Account export includes saved imports with provenance/restrictions and unresolved cleanup state; it does not add current device-only steps. Account deletion covers connections, imports, grants, cursors, outboxes and credentials. Callbacks/replayed uploads cannot resurrect a deletion-pending/deleted account. External deletions may require an active installation and restored write permission: keep a minimal permitted deletion receipt, expose pending cleanup, and document manual platform removal when automatic cleanup is impossible.
8. Export only eligible Mizyun-origin confirmed records. Ignore Mizyun's own health-store records on import. Imported records and aggregates/AI outputs derived from restricted imports cannot become eligible through copying, relabeling or confirmation. Keep source rights lineage through every transformation.
9. Stable opaque sync identities and monotonic versions prevent repeated exports: HealthKit sync identifier/version; Health Connect client record ID/version. Never put backend user IDs, access tokens or secrets in platform metadata. A meal can produce several HealthKit nutrient samples; record partial success and retry only missing items. A health export failure never rolls back a user's saved Mizyun meal/workout.
10. Update/delete only records Mizyun wrote. Maintain per-platform mappings for edits and deletion. A revoked write grant may leave cleanup pending; do not display “deleted everywhere” until confirmed. Date/DST/travel handling preserves the observed interval and original offsets; sleep associates nights/naps with an explicit display rule and unions overlapping asleep intervals from the selected source.

### INT-08 — Read-only developer pilot

**Files:** [NEW] `packages/contracts/src/developer-api-v1.ts`; [NEW] pure field/lineage grant policy in core; [NEW] authorization provider adapter after spike; [NEW] developer grant repository/migration; [NEW] `apps/api/src/modules/developer-api/`; [NEW] Connected apps mobile UI and developer docs/sample client; [MODIFY] account lifecycle and token admission boundaries as required.

Begin with registered pilot applications and synthetic sandbox data. Registration includes purpose, owner/contact, privacy/deletion policy and exact redirects. Application review is about external data access; it must not reintroduce founder approval for ordinary Mizyun AI admission. Do not give partners app-session tokens, service-role keys or full account-export access.

Use a mature OAuth authorization-code implementation with PKCE S256, exact redirect matching, state, short-lived audience-bound access tokens, refresh replay protection/rotation and revocable grants. Preferred boundary is a dedicated developer token issuer/audience accepted only by the developer API. External tokens must be rejected by internal app routes, account export/deletion, AI, Storage, PostgREST and RPC surfaces. Never forward them as owner-wide Supabase credentials.

The current deployed self-hosted Auth version was not inspected. Supabase's documented OAuth server is beta; its published supported scopes are OIDC identity scopes, with custom scopes currently unavailable. Its client tokens still carry a user identity and can inherit existing `auth.uid()` ownership policies. Therefore its existence does **not** provide our data scopes or isolation. INT-08 starts with a spike comparing a separate mature issuer to verified self-hosted capabilities. If reusing Supabase, prove client-aware restrictive admission across every legacy API/table/storage/RPC policy; adding another permissive RLS policy is insufficient. Record the accepted choice in an ADR before runtime changes.

`GET /developer/v1/me` returns a pairwise opaque subject and grant information, not email/profile identity by default. Grant review specifies categories and a date interval; widening any interval/category requires consent. Responses use explicit allowlist schemas, bounded date queries (proposed max 31 days per request), max 100 rows/page and signed cursors bound to app/owner/grant/filter. Revocation blocks future reads and refresh immediately through a live grant revision check; fail closed on unavailable grant state and recheck before emitting a prepared response. No long-lived stale grant cache.

Use a least-privilege projection/repository boundary that verifies owner, client, permission, dates and lineage for every row/aggregate. Imported restrictions also taint derived summaries and AI output; relabeling does not restore eligibility. Rate/volume limits and payload-free access logs are per app and owner; published quotas follow pilot load evidence. Pilot terms cover purpose, retention, deletion requests, onward sharing and incident response. Disconnect cannot erase every copy a partner already received: show that limitation and provide tracked deletion instructions/receipts rather than an unverifiable guarantee.

Writes, webhooks, MCP exposure, data brokers and AI provider calls are deferred. If writes later exist, start with user-reviewable drafts and independent cost/consent policy; no unlimited AI entitlement for external developers.
