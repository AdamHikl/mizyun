# ADR-0041: Release-owned Coach app capability knowledge

Date: 2026-10-04. Status: Accepted for local implementation. Work: [#205](https://github.com/AdamHikl/mizyun/issues/205). Requirements: COACH-02–05, COACH-07, COACH-12, NUTR-REC-001, ARCH-02.

The Coach's manually maintained navigation prose omitted implemented recurring meals and still named the obsolete Account tab. Model training and personal grounding cannot establish what this app release implements. Tool absence does not mean the app lacks a feature.

Keep a typed, provider-neutral, release-owned capability catalog in `packages/agent-runtime/src/app-capabilities.ts`. Supply its guidance in the trusted system policy on every initial and tool continuation request. Product facts remain separate from untrusted conversation/memory/tool data and confirmed personal evidence. Catalog descriptions distinguish implementation, account/build availability, and mutations the Coach cannot perform. Unknown capabilities require qualified uncertainty rather than confident denial. Update catalog guidance/version whenever a user-facing behavior or navigation changes; review the actual UI and conditional access boundaries.

Recognized simple recurring-meal setup questions return catalog help directly after input screening/moderation and before personal memory/model use; output moderation still runs. This response explains explicit UI setup and never creates a schedule or asserts consumption. Detailed/compound/personal requests continue through grounded Coach. Explicit future scheduling commands are excluded from one-off food drafting independently of the canned-help classifier. Existing API authentication, ownership, adult consent and limit reservation precede this path.

`pnpm test:coach-feature-knowledge`, required by `pnpm check`, compares catalog ownership with every repository feature and exact mobile route. Engineering-only features need an explicit reason. Added/removed/renamed routes, unclassified features, duplicate ownership and blank guidance fail the gate. No wildcard route coverage is allowed. Semantic changes inside an existing route still require human/non-author review and regression updates; structural coverage does not guarantee arbitrary model correctness. Live model/device acceptance stays separate and gated by BEFORE_TESTING.md.

Primary sources read 2026-10-04: [Gemini system instructions](https://ai.google.dev/gemini-api/docs/text-generation#system-instructions-and-other-configurations) support the existing system-policy transport; [prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies) recommend explicit relevant context and evaluation. These support the transport/design choice, not a factual-accuracy guarantee. No SDK/API migration, vector store, external index or user-data enrichment is introduced.
