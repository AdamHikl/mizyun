# ADR-0079 — Local-first private photos with optional backup

- Status: accepted for Dev implementation, 2026-10-22. Production release not authorized by this ADR.
- Supersedes in part: ADR-0049 (server-retained meal thumbnails as the only copy), ADR-0066 §5 (boulder photos always uploaded). ADR-0012 and ADR-0013 remain for progress photos and other private media.

## Context

Meal and boulder photos were stored only on the server and read through 5-minute signed links. Every launch re-signed and re-downloaded them; meal thumbnails were memory-cached, boulder thumbnails used expo-image's default disk cache. No server feature reads these stored photos (only Community media is read server-side), so the server copy exists only to show them again. Adam chose (2026-10-22) a local-first model: photos stay on the phone, a server copy is an opt-in backup, and Community sharing keeps its own uploads.

Adam's decisions: scope is meal and boulder photos (progress photos stay server-backed — their timeline is server-defined); keeping a meal photo on the phone is free while meal backup remains Pro; boulder backup is free; the backup setting starts off for every account, existing backups stay and are saved to the phone when viewed.

Platform facts checked 2026-10-22: Expo SDK 57 `Paths.document` is not purged by the system ([FileSystem](https://docs.expo.dev/versions/v57.0.0/sdk/filesystem/)). The app's Android backup rules (generated by expo-secure-store) include only shared preferences, so files are never in Android Auto Backup; Auto Backup is also capped at 25 MB per app ([Android Auto Backup](https://developer.android.com/identity/data/autobackup)). iOS device backups include the app's Documents directory.

## Decision

1. **Device library.** `apps/mobile/src/features/private-photos` keeps photos under `Documents/private-photos/<account>/<meal|boulder>/<uuid>.jpg`, keyed by meal entry id or ascent id, with an `index.json` recording the server asset id when a backup exists. Keys must be UUIDs; writes go through a `.part` file and a size cap (meal 256 KiB, boulder 15 MiB). Device copies render with expo-image `cachePolicy="none"`; signed server URLs never use a disk cache.
2. **Display.** The device copy is shown first, without network and without Pro. When an entry has a backup the phone lacks (or the recorded asset differs), the signed URL is read once and downloaded into the library, so later views are local. The meal list prefetch downloads instead of warming the image memory cache.
3. **Saving.** Keeping a meal photo saves the existing 640 px metadata-free thumbnail to the library (free). Boulder photos save the existing 2048 px re-encode. Nothing is uploaded unless **Back up photos** is on; meal backup also requires a fresh Pro confirmation and stays Pro-enforced on the server.
4. **Back up photos** (Account → Privacy & data). A per-account SecureStore preference, off by default and treated as off when unreadable. While on, a root bridge uploads device-only photos when the app becomes active (at most 20 per run, every 10 minutes, one run at a time). Turning it off offers to keep or remove existing backups.
5. **Removing backups.** `GET /v1/photo-backups` lists the caller's backed-up meal and boulder photos (owner-scoped, no Pro). The phone saves each photo locally first and only then deletes the server copy (`DELETE /v1/food-entries/:id/photo`, new `DELETE /v1/bouldering/ascents/:id/photo`). A photo that cannot be saved first — for example a meal photo after Pro lapsed, because reads are Pro-gated in SQL and Storage policy — keeps its backup and is reported.
6. **Boulder linking.** New `PUT /v1/bouldering/ascents/:id/photo { assetId }` links an owned `workout` asset after the fact through the existing `boulder_ascent_update` RPC, so backfill needs only the ascent id. No migration.
7. **Lifecycle.** Removing a photo deletes the backup first, then the device copy. Deleting a meal or ascent removes the device copy. Account deletion removes the account's library folder and backup preference and reports incomplete cleanup like other local data. Sign-out keeps the per-account folder, as it already does for photo drafts.
8. **Copy meal** copies the source's device photo (downloading its backup first if needed) to the new meal, and backs it up only when the setting is on. The source copy replaces the earlier staged-bytes recovery.

## Consequences

- Photos load instantly and work offline; backed-up photos cost one download per device.
- With backup off, a lost phone, app deletion or a phone change loses the photos (Android always; iOS unless restored from a device backup). The setting copy says so.
- A meal photo removed on another device stays on this phone's copy until removed here; we do not auto-delete local copies from possibly stale lists.
- Account export lists only backed-up photos; device-only photos are not in the server export (follow-up).
- Privacy policy and Store disclosures change: meal and boulder photos are stored on the device and on Mizyun's servers only when the user turns on backup. Store labels keep declaring Photos (backup, Community media and feedback attachments still collect them); on Google Play the photo collection becomes optional. The live policy and Store answers must be updated with the release that ships this, not before.
- Retry of a failed backup is automatic; the per-meal "Retry photo" remains only for pending uploads created by earlier versions.

## Acceptance

Independent sensitive review, focused tests for the library, preference, sync, meal and boulder flows and the new routes, full `pnpm check`, Dev deploy, and device journeys on iPhone and Android: keep a photo with backup off (no server asset), relaunch offline, turn backup on (upload), view on a second device (download once), remove backups (saved locally first), account deletion. Source checks do not prove device behaviour.
