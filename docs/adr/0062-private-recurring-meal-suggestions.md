# ADR-0062 — Private recurring meal suggestions

Date: 2026-10-13. Status: accepted for source implementation; Dev/native/pilot acceptance open. Requirement: NUTR-REC-002; issue #242.

## Decision

Offer one contextual card on Home/Meals after three consecutive local days of exact confirmed meal identity at any time of day; the proposed time is the rounded median (amended 2026-10-15, #252: copies are saved when Copy is tapped, so a 90-minute window missed real habits). Explicit copies count, including copies of automatic entries; server occurrence-ledger entries and surviving automatic markers do not. Detection is pure domain code and invokes no model/provider. Normalize NFC and explicit whitespace, fold ASCII case only, preserve missing nutrition versus zero, and use exact basic macros/grams. Compact same-minute duplicates and fail closed on incomplete or excessive search history.

User authorization creates a schedule, rather than merely opening an editor. Daily begins tomorrow; Change previews custom time/weekdays and uses the same acceptance boundary. Profile/device timezone disagreement requires a choice and fresh detection. Accepted schedule timezone remains fixed across travel. Existing management handles pause, skip, stop and edits. Durable30-day/permanent family dismissal and global controls never disable existing schedules.

Acceptance is an authenticated database transaction under the existing owner lock. Revalidate complete source/evidence independently of client hashes, reuse an equivalent current schedule, or create and skip today atomically. An immutable operation receipt is checked before live-evidence logic; replay never skips tomorrow. The reciprocal manual-create guard prevents suggestion-first duplicates. Accepted/stopped suggestions do not resurrect. Preserve ordinary schedule worker, entitlement and occurrence behavior.

Owner-only RLS tables store family decisions, preferences and receipts. Account export paginates each by its actual primary key; deletion blocks new admission and clears all state. Mobile persists the operation before transport in encrypted, bounded SecureStore chunks with repairable journals. Lifetime fences retire reads/actions on logout/account changes; unknown outcomes resolve the same operation. Cached success rereads schedule status before presenting it. Backgrounding hides actions/impressions; foreground refresh redetects current timezone before enabling the card. Cleanup tombstones make interrupted expected-operation deletion recoverable. Request bodies and candidate path segments are redacted, including default Fastify log messages.

Amendment 2026-10-15 (weekly pattern): a second policy `mrs-weekly-2w-v1` (`weekly_pattern`) looks at the last 14 local days. A weekday (0 = Sunday, PostgreSQL `dow`) belongs to W when the exact identity was logged on both of its occurrences; 2 ≤ |W| ≤ 6, today's weekday must be in W, and the source is today's fresh save. Evidence is one entry per date of W (4–12, ascending). The proposed time is the rounded lower median for even counts (`sorted[floor((n−1)/2)]`, SQL `minutes[(n+1)/2]`), and the default schedule uses exactly W, first logging on the next weekday in W. `public.recurring_suggestion_validate_weekly` independently re-derives dates, pairing, identity, freshness, time, weekdays, digest and candidate ID under the same locks; daily proposals, cards and receipts are unchanged. An active schedule with the same identity and timezone covering W suppresses the offer. Detection loads 14 local days. Priority: each weekday slot is on (both occurrences), off (neither) or mixed (one); a weekly proposal with no mixed slot wins over daily, so a clean two-week Mon–Fri rhythm is never offered as every day. Otherwise daily wins when it matches, so a daily logger who skipped one day, or first-week history, still gets daily. This ranking is core-only; SQL validates whichever proposal is offered.

## Alternatives and consequences

A card avoids new notification permissions and sensitive lock-screen content. Fuzzy meal matching, photo reuse, grouped meals, generalized automation and proactive advice remain outside v1. Exact matching may miss separately estimated servings. Three days is a product hypothesis; changing policy requires coordinated truthful copy/contracts. Pilot analytics is deferred and must not count generated food records as deliberate engagement or confirmed intake.
