# ADR-0080 — Store billing through RevenueCat with server-verified entitlements

- Status: accepted for Dev implementation, 2026-10-26 (#332, go-to-market plan Section 3.7 item 1). Production purchases stay off (`BILLING_ENABLED` unset) until Adam enables them; this ADR is not a release trigger.
- Extends: ADR-0029 (only a verified entitlement may set `plan_tier = 'paid'`). Beta Pro Pass (`beta_pro_requests`) keeps granting paid.

## Context

Mizyun needs a Pro subscription on the App Store and Google Play: EUR 7.99/month, EUR 49.99/year, a EUR 34.99 founding-member year for the first 100 payers, a 14-day trial and no lifetime plan (Adam, 2026-10-26). Prices, trials and the founding offer are Store and billing-console configuration, never code. `profiles.plan_tier` is already server-owned: clients cannot write it (`20260908140000_server_owned_tier_authority.sql`) and every Pro gate (AI caps in `packages/config/src/ai-tier.ts`, advanced nutrients, recipes, photo backup) reads it or an approved Beta Pro request.

Options, from current primary documentation (see `docs/RESEARCH_LOG.md`, 2026-10-26):

- **Native.** App Store Server Notifications V2 (JWS signed payloads with an x5c chain to Apple's root), App Store Server API calls with an ES256 key, StoreKit 2 transactions sent to our server; separately Play Billing Library 8+ on the device, Real-time developer notifications through Google Cloud Pub/Sub, `purchases.subscriptionsv2.get` and acknowledgement. Two verification stacks, two notification channels, Pub/Sub infrastructure and Store credentials on our server.
- **RevenueCat.** One SDK for both stores (`react-native-purchases`, works with an Expo development build, no config plugin on SDK 57), one webhook for both, and a REST API that returns the current entitlement. It handles receipt validation and Play acknowledgement. The app ships only RevenueCat's public SDK keys; the secret key and webhook secrets stay on the server.

## Decision

1. **RevenueCat**, `react-native-purchases` pinned to 10.12.2 (published 2026-10-08; purchases-hybrid-common 19.10.0). One entitlement, id `pro` (`REVENUECAT_ENTITLEMENT_ID`), attached to the monthly and yearly products; offerings select which packages show (`REVENUECAT_OFFERING_ID`, default the current offering), so a founding-member offering is a console change.
2. **App user id = Supabase user id.** The app configures the SDK with the signed-in user's UUID and calls `logIn` on account switch, never `logOut` (which mints an anonymous id) and never sends email or other attributes. The SDK is configured only when the user opens the plan screen, so people who never look at Pro do not contact RevenueCat. Keep RevenueCat's default restore behaviour "Transfer to new App User ID"; the server handles transfers (item 4).
3. **Server is the only authority.** The webhook is a trigger, not data. `POST /v1/billing/revenuecat/webhook` checks the optional dashboard `Authorization` value and requires RevenueCat's HMAC signature (`X-RevenueCat-Webhook-Signature: t=…,v1=…` over `"<t>.<raw body>"`, 5-minute tolerance, constant-time compare) on the raw bytes received. It then re-reads each named account from `GET /v1/subscribers/{id}` with the secret key, as RevenueCat recommends, and decides with the pure rule in `packages/core/src/billing.ts`: active while the expiry (or grace period) is in the future, not refunded, and from a production purchase unless sandbox is allowed (an unknown environment, for example an unmatched or ambiguous Play base plan, is refused too). Event fields such as `expiration_at_ms` are never trusted.
4. **Identity.** Only UUID-shaped ids among `app_user_id`, `original_app_user_id`, `aliases`, `transferred_from` and `transferred_to` are considered, at most 10; each must be an existing profile before RevenueCat is asked (its lookup would otherwise create a customer). A transfer re-reads both sides, so the old account loses Pro and the new one gains it.
5. **Idempotency and order.** `billing_webhook_events` records each event id; a processed id returns 200 without work (replay), an unfinished one is retried. `billing_apply_entitlement` writes only when the snapshot's RevenueCat `request_date` is not older than the stored one, so a slow or reordered read never overwrites a newer state. Processing failures return 503 so RevenueCat retries (up to 5 times over about 80 minutes); bad signatures return 401, unreadable payloads 400.
6. **Database.** `subscription_entitlements` (one row per user, `user_id` primary key, owner `select` RLS, service-role writes only, cascades on account deletion, included in account export). `billing_recompute_plan_tier` (SECURITY DEFINER, empty `search_path`, service role only) sets paid while a subscription is active **or** a Beta Pro request is approved, sets free when a subscription that granted paid ends, and otherwise leaves the tier as an operator set it, so a sync that finds no purchase never removes a direct paid grant. Applies and the Beta Pro rejection trigger lock the profile row first; the trigger now keeps paid while a subscription is active. The ledger stores no user id, is pruned after 90 days and is not exported.
7. **App endpoints.** `GET /v1/billing/entitlement` returns the plan tier, its source (`subscription`, `beta_pro`, `manual`, `none`), the stored entitlement, whether purchases are enabled, and the public SDK keys. If the stored row is active but its period has passed (expiry webhook not yet received), the server re-reads RevenueCat before answering. `POST /v1/billing/entitlement/sync` re-reads the caller's own entitlement after a purchase or restore (body ignored, at most once per 10 seconds per user and 120 times per minute per API process, so app traffic cannot exhaust the shared RevenueCat key that webhooks need). The app shows Pro only from these responses.
8. **Flags.** `BILLING_ENABLED` is on in Dev unless set to `false`, off elsewhere unless `true`, and billing turns on only when `REVENUECAT_SECRET_API_KEY` and `REVENUECAT_WEBHOOK_SIGNING_SECRET` are present and a service-role client exists. With billing off, the webhook route does not exist, `purchasesEnabled` is false and no SDK key is sent. `BILLING_ALLOW_SANDBOX` defaults to true in Dev and false elsewhere, so TestFlight and Play licence-tester purchases cannot grant Production Pro by default. Public keys: `REVENUECAT_IOS_PUBLIC_KEY`, `REVENUECAT_ANDROID_PUBLIC_KEY`; optional `REVENUECAT_WEBHOOK_AUTHORIZATION`.
9. **Plan screen** (Account → AI coach → Mizyun Pro plan): current plan first, then the Store's localized prices (yearly selected), the renewal disclosure, the trial only when the Store reports eligibility, Subscribe, Restore purchases, Manage or cancel subscription (`https://apps.apple.com/account/subscriptions`; `https://play.google.com/store/account/subscriptions?sku=…&package=…`), Terms of Use and Privacy Policy. The free tier stays fully usable; nothing is paywalled at install. The account-deletion card says that deleting the account does not cancel a Store subscription.

## Consequences

- One vendor processes purchase history and the Supabase user id; App Privacy and Data safety must declare Purchases / Purchase history and a User ID linked to the user (`docs/STORE_LISTING_DISCLOSURES.md`). RevenueCat's own customer record is not erased by account deletion yet (#337).
- If the expiry webhook never arrives (all RevenueCat retries fail) and the user never opens the plan screen, `plan_tier` can stay paid past the period. A periodic re-read of lapsed active rows (#338) is required before Production purchases are enabled.
- A user whose paid tier was granted directly loses it when a subscription they later buy ends; operators re-grant if needed.
- Pending purchases (Ask to Buy, slow payment methods) finish the next time the SDK is configured or through the webhook.
- Manual console steps for Adam (none done by this change): create the subscription group/products and base plans with the adopted prices, 14-day trial and founding offer in App Store Connect and Play Console; add the Paid Applications agreement, banking and tax; create the RevenueCat project, apps, `pro` entitlement and offerings; set the webhook URL `https://<api host>/v1/billing/revenuecat/webhook` with signing (and optional Authorization) secret; put the secrets and public keys in the Dev (and later Production) server environment.
- Rejected: native StoreKit 2 + Play Billing (two stacks and Pub/Sub); trusting client `CustomerInfo` or webhook payload fields (violates ADR-0029); a hard paywall at install (go-to-market plan Section 5.2).
