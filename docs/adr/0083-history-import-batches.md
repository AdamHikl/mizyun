# ADR-0083: History import batches from Hevy, Strong, Strava export and generic CSV

Date: 2026-10-26. Status: accepted for Dev under [#333](https://github.com/AdamHikl/mizyun/issues/333) (go-to-market plan adopted by Adam on 2026-10-26, Section 3.7 item 2). Production, native/device and real-export acceptance remain open.

## Context

Switching cost is the main objection from people with a year of logs in Hevy or Strong, and runners keep their history in Strava. Mizyun already stores strength workouts with typed sets (warmup, drop, failure; ADR-0068 timed sets), runs with provenance (ADR-0065) and custom exercises (ADR-0075). Strava's API terms restrict AI and aggregation uses of API data, so the API is never called; the user's own account-export archive is the only Strava source. No vendor publishes a reachable column specification (see the 2026-10-26 research log entry).

## Decision

1. **Sources.** A Hevy workout CSV, a Strong CSV (comma or semicolon variants), `activities.csv` from the user's own Strava account archive, and a Mizyun generic workout CSV (`date`, `exercise` plus optional `workout`, `set_type`, `reps`, `weight`, `weight_unit`, `duration_seconds`, `distance`, `distance_unit`, `rpe`, `notes`). The user picks one file on the phone; the app sends its text only. Strava GPS files and every other archive file are never read or uploaded.
2. **Pure parsing.** `packages/core` parses files into normalized workouts and runs (`parseHistoryFile`), with row-level issues instead of whole-file failure, and suggests catalog matches (`summarizeHistoryExercises`). Files with local wall-clock times (Hevy, Strong, generic) use the phone's named time zone; explicit ISO offsets win. Units come from the file where it names them, otherwise from the user's choice in the preview. Strava imports runs only (`Run`, `Trail Run`, `Virtual Run`); other activity types are counted and skipped.
3. **Preview, then explicit confirm.** `POST /v1/history-imports/preview` returns counts, the date range, issues, skipped Strava types, the exercise list with suggested catalog matches, and how many records were already imported or overlap existing ones. Nothing is written. `POST /v1/history-imports` repeats the file and carries the user's mapping for every exercise: a catalog entry, a custom exercise (created as an ADR-0075 custom record unless a saved one with that name exists), or skip.
4. **Batch identity and idempotency.** The client generates the batch id once per confirmed preview. The server stores `public.history_import_batches` (owner RLS, `user_id` index) with a SHA-256 digest of the file text, format, time zone, units and mappings. Replaying the same id with the same digest resumes or returns the stored batch; a different digest is `409`. Records are written in chunks of at most 200 workouts or runs and 2,500 sets (the RPC refuses more than 5,000) through security-definer RPCs, so each chunk is one short statement under the 8 s `authenticated` timeout (about 0.25 s measured locally); a replay of an already written chunk is a no-op even after the batch completed. Each imported row carries `import_batch_id` and `import_key` (`<format>:<externalId>`: Strava Activity ID; Hevy/Strong start instant; generic start instant plus name). A partial unique index on `(user_id, import_key)` makes a retried chunk, a re-import of an overlapping export and a concurrent duplicate request write each record once. Records that overlap an existing run (for runs) or strength session (for workouts) are skipped by default so Health-imported or manually logged copies are not doubled; the user can include them.
5. **Provenance.** Strength workouts keep `source = 'file_import'` and the batch columns; their details add `entryMode: "history_import"` and `importSource: { format }` for display. Strava runs use the run model with `runSummary.origin = { kind: "file_import", format: "strava", externalId }`, `durationBasis: "elapsed"` and an observed start; like Health imports, their date, start, duration, distance and origin are read-only, and name, notes, environment and effort stay editable. Provenance columns and `source` can only be set by the import RPCs (row trigger); the workout adapter no longer rewrites `source` on update, so editing an imported workout keeps it.
6. **Deletion as a batch.** `DELETE /v1/history-imports/:id` removes every workout and run still linked to the batch (sets cascade) in slices of at most 100 records and about 5,000 sets per RPC call, then the exercises the batch created that no set of the user references, then the batch row. An interrupted undo leaves the batch listed with fewer records and can be repeated. Records the user deleted individually are already gone; records they edited are still removed with the batch. `GET /v1/history-imports` lists batches with counts for the Import screen's undo.
7. **Compatibility.** `GET /v1/runs?include=imports` keeps returning only manual and Health runs, because installed builds parse origins strictly; `include=all_imports` adds file imports and is sent only by builds with history import enabled. Strength workouts keep wire `source: "manual"`; extra detail keys are ignored by older clients.
8. **Use.** Imported strength workouts count like logged past workouts (history, progression, Coach grounding). Imported Strava runs count in run history and weekly totals and are excluded from Coach/AI grounding, Community and outbound Health exports, like Health imports (ADR-0065).
9. **Limits and availability.** Request bodies are capped at 26 MiB (8,000,000 characters of up to 3 UTF-8 bytes) and file text at 8,000,000 characters, 200,000 rows, 5,000 workouts, 5,000 runs, 500 sets per workout and 400 distinct exercises. Routes are enabled when `MIZYUN_ENVIRONMENT=dev` or `MIZYUN_HISTORY_IMPORTS_ENABLED=true`; the mobile entry follows `extra.enableHistoryImports` (Dev on).

## Consequences

- Date formats, Strong set-order letters and Strava `Activity Date` as UTC are assumptions backed by fixtures, not vendor documentation; a real export from each app is an acceptance item before Production.
- Corrections made later in the source app are not synced; the user deletes the batch and imports again.
- Hevy, Strong and generic import keys are start instants computed with the phone's time zone, so re-importing the same file with the phone in another zone is not recognised as a duplicate (overlap skipping still catches shifts shorter than the session). Keying on the file's wall-clock text is a possible follow-up.
- File text is cleaned of NUL and other control characters and cut by code point, because Postgres text and JSON cannot store them.
- Import and undo writes take the global Community statement lock briefly per chunk, as every set write does; the small chunks keep that short.
- A saved exercise with the same name is reused even if its tracking type differs, and undo removes custom exercises the batch created even when a routine plans them by name (ADR-0075 routines reference names).
- Builds with history import ask for `include=all_imports`, which an API without this change rejects: deploy the API before such a build, and add a client fallback before any broader rollout.
- A whole import of several thousand workouts takes several requests' worth of database work inside one confirm request; a lost response is recovered by retrying with the same batch id.
- `expo-document-picker` is a new native module, so the feature needs a new Dev binary before device testing.
- Privacy policy and Store disclosures must mention imported history before Production enablement.
