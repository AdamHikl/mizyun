# Community simulator scenario matrix — 2026-10-10

This is a plan, not passed acceptance. Run the same compact matrix on iOS and Android simulators against confirmed Dev targets. Use two distinct disposable synthetic Dev accounts A/B with Community enabled; never use real health/person data. Record each platform independently as PASS, FAIL, BLOCKED or NOT TESTED, exact client/backend candidate, simulator OS/model, aliases, steps and redacted evidence. Simulator results do not close physical-device or external gates.

Inventory source: [remaining issues](../../COMMUNITY_REMAINING_ISSUES_2026-10-08.md), dated 2026-10-08; an initial GitHub read failed, then a successful final live refresh on 2026-10-10 confirmed 27 selected open issues: #137, #140, #142–162 and #166–169. #141 and #224 remain closed; #224 is included only for UI regression coverage. Current UI source has Feed/People/Messages/Me (`apps/mobile/src/features/community/ui/index.tsx`); the older [test guide](../../COMMUNITY_DEV_TEST_GUIDE_2026-10-02.md) contains historical Together labels/build identifiers. Locate equivalent current controls and record actual labels instead of assuming those older labels remain.

Prerequisites: verify client/API/Supabase all Dev and exact artifact/source identifiers, account admission and independent sessions; prepare only synthetic completed workouts, ordinary numeric routine targets and a plain-object image. Include a private title/note sentinel that must never appear remotely. Keep mutual follows until expansion checks finish. Use another simulator/session where necessary for simultaneous recipient revocation; sequential account switching cannot prove a live two-session boundary. Do not alter staff roles, push configuration, server flags or services to unblock a scenario.
