Prepared 2026-09-17, inventory updated 2026-09-18, and **completed through public cutover, device acceptance, deployment retargeting, and first off-host restore drill on 2026-09-19**. The Helsinki CX23 serves the unchanged Dev and Production public hostnames. - Installed pinned x86-compatible services and exact Pi application SHAs on the CX23, with Production and Dev database/gateway/API ports bound only to loopback. A cold reboot recovered both stacks. At the post-cutover checkpoint the VM had about 1.4 GiB available RAM and 24 GiB free root storage; CX23 remains acceptable for this initial workload, with CX33 the first rescale option.

- A clean restore exposed two recovery-critical omissions in the prior backup format: database ownership/ACLs were omitted, and ordinary tar did not retain the extended attributes required by Supabase local Storage reads. The cutover therefore used full owner/ACL-preserving custom dumps and xattr/ACL-preserving Storage archives. Keep these requirements in #104 and any future `backup-production.sh` hardening.
- Exact table-count comparison passed after ignoring only two VM-created, zero-row Realtime date partitions. Extension versions and Storage byte checksums match. Correct Prod/Dev keys return Auth health 200 and cross-environment keys return 401. Existing Production media passed authenticated and signed downloads locally and through the public hostname.
- Switched the existing remotely managed Cloudflare tunnel by disabling it on the Pi and enabling it on the VM. Both API health routes and both keyed Supabase Auth health routes return public HTTP 200; VM logs prove public-host traffic reached the VM. The Pi tunnel, APIs, Production containers and Production database are stopped, with no port 5432 listener; its persistent data and final archives remain intact. The Pi is a frozen recovery source, not an active replica. Any rollback after a VM write requires a new freeze and reverse transfer/reconciliation.
- Founder acceptance (2026-09-19): the founder tested both installed Dev and Production apps after cutover and reported that both appear to work. Deployment tooling and primary-host runbooks now target guarded non-root Hetzner identities and cannot default to `rpserver`. ## Decision

**Use the already-provisioned CX23 in Helsinki** as the target for staging and measurement. It reports Ubuntu 24.04.4 x86-64, 3.7 GiB usable RAM, a 38 GiB root filesystem with 1.2 GiB used, no swap, SSH listening on port 22, and no Docker command installed (read-only checks, 2026-09-18). The founder reports key-only SSH, a Hetzner firewall allowing port 22 only, and €5.99/month including IPv4 excluding VAT; the firewall and billing settings were not verified in the control plane. The Pi 5 has 4 GB RAM and has hosted both environments. Keep CX33 as the first rescale option if a two-stack load/restart/restore rehearsal shows memory, CPU or disk pressure. Do not infer capacity from nominal RAM alone: CX23 has two shared vCPUs versus the Pi's four cores.

The earlier unavailable-plan discussion is superseded by the founder's successful CX23 provisioning. [Hetzner's price table](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/) lists CX23 at €5.49/month excluding VAT/IPv4, consistent with the founder's €5.99 including the €0.50 IPv4 charge. Backups and other storage add cost.

The Pi's 2026-09-17 snapshot showed 3.9 GiB total RAM, 2.8 GiB used, 1.1 GiB available, 218 MiB swap used, and 20 GiB used on a 29 GiB root filesystem. Both API services were active, as were 17 Supabase containers (six Dev, eleven Production); the Production container images include `supabase/postgres:17.6.1.136`, `supabase/gotrue:v2.189.0`, and `supabase/storage-api:v1.60.4`. This is practical evidence that the lean topology fits on a 4 GB host **at that moment**, not evidence of peak or cold-start headroom. [Supabase's Docker sizing](https://supabase.com/docs/guides/self-hosting/docker) gives 4 GB RAM/2 cores/40 GB SSD as minimum and 8 GB+/4 cores+/80 GB+ as recommended for **one full default stack**; those figures are not a direct verdict on Mizyun's customized deployment. Gate Production on a two-stack load/cold-reboot test, disk-growth check, and full database-plus-Storage restore rehearsal. Rescale to CX33 if headroom is inadequate; Hetzner allows same-architecture rescaling, but expanding the disk prevents later disk-size downgrade.

If one host for both environments proves unsafe, isolate Dev on a second VM or keep it on the Pi temporarily rather than letting Dev starve Production. One CX23 with both environments is a pilot/early-production topology, not high availability.

The Pi is ARM64 and CX23 is x86-64. Pull compatible pinned images and use a **logical** PostgreSQL dump/restore plus private Storage file copy; do not clone the Pi disk. PostgreSQL documents that `pg_dump`/`pg_restore` archives are portable across architectures. Verify that the existing Supabase component versions and any extensions work on x86 before restoring real data.

The VM price is not the total: verify primary IPv4 charges (or an IPv6-only/Tunnel design), Hetzner Backups, encrypted off-host database and Storage backups, storage growth, and VAT. Hetzner Backups cost an additional 20% of the server price and are useful for machine recovery, **not** a substitute for independently restorable database plus private Storage backups. Supabase self-hosting leaves backup, maintenance, monitoring, and recovery to the operator.

Hetzner server Backups do **not** include attached Volumes; if data lives on a Volume, protect it separately. Replication of a Volume is not backup. Health data and backup archives require an explicit encryption and EU-data-location decision; do not assume cloud disks are encrypted for Mizyun by default.

## Current backups and recovery gap (verified 2026-09-18)

- Every Production code promotion invokes `scripts/backup-production.sh` before migration. It creates a timestamped directory on the Pi under `/srv/mizyun/backups/` with a PostgreSQL **custom-format logical dump**, a gzip archive of private Storage files, and SHA-256 checksums. The script restricts file permissions. The Pi's latest archive is `20260918T080150Z` (about 534 KB database, 4.3 MB Storage); both files exist. The preceding archive `20260917T054642Z` passed checksum verification on the Pi. A checksum verifies bytes, **not restorability or freshness**.
- This Mac has a loaded `com.mizyun.backup-sync` LaunchAgent, scheduled every 1,800 seconds while the Mac is awake. Its script attempts one fresh Pi backup per calendar day, rsyncs the archive directory to `/Users/adam/Backups/mizyun`, and checks the latest archive. The 2026-09-18 10:01 CEST run created/copied `20260918T080150Z`; the Mac log reports both files' checksums passed. There is no Pi backup timer in the current `systemctl list-timers` output. Therefore the automatic backup path depends on this Mac being on, connected and able to reach the Pi.
- Gaps: no demonstrated restore of database **and** Storage on an independent machine; no scripted retention/pruning or archive-level encryption; no alert that proves a _fresh_ backup was created. The Mac script proceeds to sync old archives if remote generation fails and can mark a day successful. The current dump/archive do not themselves include host configuration, secret files, PostgreSQL global roles or Supabase's `db-config` named-volume key. Inventory whether that key protects any Vault data before relying on the dump. The database snapshot and Storage tar are taken sequentially while writes may continue, so final migration needs a write freeze and consistency checks. No Dev backup is required if Dev remains disposable/synthetic, but that policy must be explicit.

The founder accepts a long planned outage but wants **no data lost during migration**. Treat this as a lossless _planned cutover_ requirement: hold a complete write freeze across API, Auth, Storage, direct database access and background jobs; take the final paired backup after writes stop; restore and compare it before the VM accepts writes. Do not equate this with zero data loss after a later unplanned VM failure. A daily Pi backup could lose nearly 24 hours of writes; a strict zero-data-loss disaster-recovery target requires a separate, much more complex design. Define that ongoing **recovery point (maximum data loss)** and **recovery time (maximum outage)** explicitly before selecting the post-cutover backup frequency.

**Post-cutover Pi backup proposal:** keep the Pi as a geographically separate backup destination, initially retaining its old Production data read-only through an agreed rollback window. Only repurpose it after cutover acceptance; do not erase the old source to make room. The Pi's 29 GiB root filesystem had about 7.8 GiB free at inspection, so provision a dedicated encrypted external SSD and capacity/retention budget rather than relying on its root disk. Run unattended VM-origin backups independently of the Mac: a consistent PostgreSQL dump, private Storage bytes, and recovery-critical configuration/key material stored separately and securely. Transfer over a private authenticated channel to a restricted Pi backup account, with encryption, append-only or otherwise deletion-resistant retention, checksums, age/capacity alerts and scheduled isolated restore tests. Keep an additional independent encrypted offsite copy: the Pi has already experienced downtime and must not be the only recovery location. Decide whether Dev needs backup or remains synthetic/disposable. Hetzner VM Backups can complement this for OS recovery, but do not replace application backups and omit attached Volumes.

If the ongoing loss budget is much shorter than one day, evaluate PostgreSQL physical base backups plus continuous WAL archiving or streaming replication **in addition to**, not by replaying WAL onto, the current logical dumps. This protects database writes only; local Supabase Storage files need a separately consistent, versioned transfer. Synchronous database replication can protect acknowledged database commits but increases write latency and can block commits when the Pi is disconnected; it still does not make Storage files synchronous. Do not label daily backups, asynchronous replication or Hetzner snapshots “zero data loss.”

## Stages and go/no-go gates

1. **Close recovery and source inventory gates.** The Pi is online, but backup restoration and current peak headroom are not proven. Record effective Production/Dev Compose graph, mounts, named volumes, extensions, migration ledgers, service units, backup/restore paths, Cloudflare route ownership, and required Auth/SMTP/AI secrets **privately without printing values**. Record the accepted long maintenance window and lossless planned-cutover rule; choose the _separate_ ongoing failure RPO/RTO, encryption, retention, Pi external-SSD capacity and independent offsite copy. Issue #53's long-term staging gate is out of scope for this move by founder decision. Exit: a complete non-secret manifest, a fresh backup on two devices, and a successful isolated restore of database, Storage and any required key/config.
2. **Harden and prepare the existing CX23.** Verify Hetzner firewall, DPA/EU backup destination, account MFA and deletion protection. Configure a non-root operator/deploy path, OS updates, outbound tunnel/Tailscale administration, disk/RAM alerts, bounded Docker logs, and an agreed swap/rescale policy; keep database, Studio and API listeners private. Install supported Docker/Compose and pinned x86 images without exposing Production. A CX23 pilot must leave enough disk for images **and** temporary restore/backup data; if the cold-boot or restore rehearsal exhausts memory/disk, rescale to CX33 before Production. Exit: documented base image, hardening, boot/restart evidence, and only intended ports exposed. Do not copy credentials into Git or logs.
3. **Build isolated Dev first.** Reproduce the pinned Dev service graph with separate Linux user, Compose project, DB/Auth/Storage data, signing keys, and secret files. Use synthetic data. Update and test target manifests and deployment guards rather than simply pointing `rpserver` at a new host; old paths, service names, rollback, and backup assumptions must fail closed against the wrong host. Relevant future files: `[MODIFY] scripts/deployment-manifest.mjs`, `[MODIFY] scripts/deploy-dev.mjs`, `[MODIFY] scripts/deploy-remote.mjs`, `[MODIFY] scripts/promote-dev.sh`, `[MODIFY] scripts/promote-production.sh`, `[MODIFY] scripts/backup-production.sh`, `[MODIFY] deploy/raspberry-pi/*` or successor infrastructure files, and `[NEW]` target runbook/config templates. Keep Dev separate from Production by effective permissions and secrets, not only container names.
4. **Rehearse Production restore without public cutover.** Use the pinned Pi Production SHA `43917fa...` and component images initially; do not upgrade code, Postgres, Supabase and host in one step. Restore a tightly access-controlled Production backup to an isolated target. Restore **both** database metadata and Storage object bytes plus any required global roles/key material, and compare row/object counts and checksums, migration ledger, RLS, Auth identities, media reads/signed URLs, email/OAuth redirects, API routes, export/deletion, and two-user cross-environment isolation. Test whether existing refresh tokens survive with retained signing configuration; otherwise plan a deliberate sign-in requirement. Measure restore time, CPU/memory, disk and error rates. One complete, independently verified rehearsal is the minimum for this move; investigate and repeat it if any check fails. Do not rely on a VM snapshot as the only recovery path.
5. **Cut over in a controlled, potentially long maintenance window.** After a fresh `pnpm check`, independent deployment/security review, physical-device Dev acceptance, and successful Production rehearsal, announce maintenance and stop every Production write path, including API/background tasks, Auth/session writes, Storage uploads and any direct Supabase clients. Drain in-flight writes; keep the Pi as the sole source of truth. Take and verify the final database and Storage pair **after** the freeze; restore it to the VM and compare database state, Storage manifest/checksums, Auth identities and critical app journeys before accepting a new write. Switch the **existing four public hostnames** to Hetzner through a controlled Cloudflare authority change. Do not run the Pi and Hetzner as active replicas of the same tunnel against divergent databases: Cloudflare replicas do not guarantee traffic steering. Probe exact service starts, API identity, Auth, signed Storage and physical-device Production journeys, then open VM writes. Set rollback thresholds and a time limit in advance. Rolling traffic back after new VM writes is **not** a safe data rollback; if the VM fails after accepting writes, freeze again and reconcile/reverse-transfer before any source change. Keep Pi source read-only during the observation window.
6. **Operate and repurpose deliberately.** Establish verified daily encrypted VM-to-Pi application backups on the dedicated SSD, retention, freshness/capacity alerts, scheduled clean-room restores and an additional independent copy; measure the achieved RPO/RTO. Keep the old Pi Production source intact through the rollback window before repurposing space. Patch and monitor both hosts, including Pi connectivity/power and backup failures. Remove old secrets/routes/data only after reconciliation and explicit retention decision. Update `AGENTS.md`, runbooks, status, deployment evidence and issue tracking to reflect the new authority. Do not call the cutover complete until app/device, restore, isolation and first post-cutover backup/restore evidence exists.
