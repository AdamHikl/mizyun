# Hetzner backend migration plan (planning only)

Prepared 2026-09-17 from local repository commit `ed4a19784a66082a59558388fe29688545887441`. The Raspberry Pi is temporarily down; no Pi connection, live inventory, backup, deployment, or account change was attempted. This is a candidate plan, not cutover approval.

## Decision

**Prefer CX33 (x86-64, 4 shared vCPU, 8 GB RAM, 80 GB NVMe) in NBG1** for the initial two-environment move, if it becomes orderable. The founder clarified that the current Raspberry Pi 5 has **4 GB RAM** and has hosted both stacks; therefore a **CX23 (2 shared vCPU, 4 GB RAM, 40 GB NVMe) is a plausible like-for-like candidate**, not categorically too small. CX33 costs €3/month more in the user's list (€8.99 versus €5.99) for double the CPU allocation, RAM and disk, which buys useful migration and recovery headroom. The founder's screen showed every listed CX/CAX plan as unavailable. Recheck the order screen, project limits and final price at purchase. NBG1 and HEL1 are both EU locations; NBG1 is the first latency choice for Slovak users, subject to measurement and capacity.

Hetzner says plan availability changes dynamically and Console availability can be stale; refresh it and check project limits before assuming the whole region is sold out. If still unavailable, wait or ask Hetzner support about capacity rather than substituting an unsuitable region or architecture. The official price table lists CX23 at €5.49/month and CX33 at €8.49/month excluding VAT and IPv4 after its June 2026 adjustment; the user's prices appear consistent with the separate €0.50/month IPv4 charge, but the actual checkout is authoritative.

The existing Pi runs separate Dev and Production API/Supabase stacks on 4 GB RAM. That is strong practical evidence that 4 GB _can_ host Mizyun's lean topology, though it does not prove spare capacity or explain the current outage. [Supabase's Docker sizing](https://supabase.com/docs/guides/self-hosting/docker) gives 4 GB RAM/2 cores/40 GB SSD as minimum and 8 GB+/4 cores+/80 GB+ as recommended for **one full default stack**; those figures are not a direct sizing verdict on Mizyun's customized deployment. Its checked-in Dev Compose has six container memory limits totaling 830 MB, but limits are not measured usage and exclude the API process, OS, Docker, tunnel, page cache, backups and restore workspace. The live Production graph/peaks and Pi disk size are unverified. CX23 is acceptable as a **budget-first pilot and potential final host only after** a two-stack load test, disk-growth check, and database-plus-Storage restore rehearsal. CX33 is the better default margin for €3/month more. Escalate to CX43 only if measurements justify it; CX53 is not the default for this known 4 GB baseline. Prefer CX over CAX for this first move because x86-64 avoids an ARM-only image constraint; this is operational convenience, not a measured performance claim. Hetzner's shared CX CPU is burstable, not dedicated; move to dedicated resources if sustained load requires predictable CPU.

If one host for both environments is no longer acceptable, choose **two separately sized VMs** after measurement, with Production isolated from Dev. This changes the price and operations plan but avoids a common host failure domain. One CX33 or CX23 remains a pilot/early-production topology, not high availability. Do not order an arbitrary non-EU plan just because the preferred plan is unavailable.

The Pi is ARM64 and CX is x86-64. Rebuild/pull compatible container images and perform a logical database and file migration; do not expect to clone a Pi disk or use an ARM Hetzner snapshot to create a CX instance. CAX31 retains ARM64 but is more expensive in the supplied list and does not remove the data-migration work.

The VM price is not the total: verify primary IPv4 charges (or an IPv6-only/Tunnel design), Hetzner Backups, encrypted off-host database and Storage backups, storage growth, and VAT. Hetzner Backups cost an additional 20% of the server price and are useful for machine recovery, **not** a substitute for independently restorable database plus private Storage backups. Supabase self-hosting leaves backup, maintenance, monitoring, and recovery to the operator.

Hetzner server Backups do **not** include attached Volumes; if data lives on a Volume, protect it separately. Replication of a Volume is not backup. Health data and backup archives require an explicit encryption and EU-data-location decision; do not assume cloud disks are encrypted for Mizyun by default.

## Stages and go/no-go gates

1. **Recover source evidence.** While the Pi is down, inventory local configuration, deployment safeguards, image pins, Cloudflare route ownership, mobile public URLs, and any independently available _encrypted off-Pi_ backup. Do not assert the latest production state from `status.md`. When the Pi returns, record the exact running SHAs, Compose images/volumes, Postgres and Storage sizes, memory/CPU/I/O peaks, disk growth, tunnel and systemd configuration, Auth signing/SMTP/provider settings, and last verified backup. If the Pi cannot return, migration can proceed only from a separately verified backup with an explicit accepted recovery point; do not silently lose recent user writes.
2. **Provision a private target.** Check CX33 and CX23 availability and account limits in NBG1, then create an Ubuntu LTS x86-64 host with SSH keys, patching, operator MFA, restrictive Hetzner firewall, Tailscale/operator access and monitored disk/memory. A CX23 pilot must have an explicit rescale trigger and enough free disk to rehearse restoration; Hetzner can rescale within the same architecture, but expanding its disk prevents a later disk-size downgrade. Restrict Postgres, Studio, and service ports to loopback/private interfaces. Use Cloudflare Tunnel or an equivalently reviewed HTTPS ingress for the existing four public hostnames. Document all recurring charges and enable deletion protection. Do not copy credentials into Git or logs.
3. **Build isolated Dev first.** Reproduce the pinned Dev service graph with separate Linux user, Compose project, DB/Auth/Storage data, signing keys, and secret files. Use synthetic data. Update and test target manifests and deployment guards rather than simply pointing `rpserver` at a new host; old paths, service names, rollback, and backup assumptions must fail closed against the wrong host. Relevant future files: `[MODIFY] scripts/deployment-manifest.mjs`, `[MODIFY] scripts/deploy-dev.mjs`, `[MODIFY] scripts/deploy-remote.mjs`, `[MODIFY] scripts/promote-dev.sh`, `[MODIFY] scripts/promote-production.sh`, `[MODIFY] scripts/backup-production.sh`, `[MODIFY] deploy/raspberry-pi/*` or successor infrastructure files, and `[NEW]` target runbook/config templates. Keep Dev separate from Production by effective permissions and secrets, not only container names.
4. **Rehearse Production restore without public cutover.** Pin compatible image/Postgres versions. Restore a redacted or access-controlled Production backup to an isolated target. Restore **both** database metadata and Storage object bytes, compare row/object counts and checksums, migration ledger, RLS, Auth identities, media reads/signed URLs, email/OAuth redirects, API routes, export/deletion, and two-user cross-environment isolation. Test whether existing refresh tokens survive with retained secrets; otherwise plan a deliberate sign-in requirement. Measure restore time, CPU/memory, disk and error rates. Keep an off-host encrypted backup and prove an independent clean restore. Do not rely on a VM snapshot as the only recovery path.
5. **Cut over in a controlled window.** After a fresh `pnpm check`, independent deployment/security review, physical-device Dev acceptance, and a successful Production rehearsal, freeze Production writes. Take and verify final database and Storage backups; apply the final delta; confirm source/target SHAs and migrations; change the existing Cloudflare Tunnel/DNS routes to the Hetzner listeners. Probe exact service starts, API identity, Auth, signed Storage, and real Production app journeys. Watch errors, latency, resources and user write success. Set rollback thresholds and a time limit in advance. Rolling DNS back after new writes is **not** a safe data rollback; predefine write handling/reconciliation and keep the Pi or backup source read-only during the observation window.
6. **Operate and decommission deliberately.** Automate encrypted off-host database plus Storage backups with retention, restore drills, monitoring/alerts, patching and capacity thresholds. Keep the old host/backup intact for an approved rollback window; remove old secrets/routes/data only after reconciliation and explicit retention decision. Update `AGENTS.md`, runbooks, status, deployment evidence and issue tracking to reflect the new authority. Do not call the cutover complete until app/device, restore, and isolation evidence exists.
